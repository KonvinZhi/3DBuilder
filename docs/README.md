# 文档入口

新会话先读根 [README](../README.md) 和 [项目约定](../AGENTS.md)，再按当前任务选择以下入口。每条事实只有一个主要维护位置，其他文档通过链接引用。

| 要了解的内容 | 主要维护位置 |
| --- | --- |
| 服务对象、产品方向、有效业务约束、候选功能和待确认问题 | [产品范围与候选构想](product.md) |
| 现在真正存在的实现、组成与边界 | [工程现状](architecture.md) |
| 检查命令、覆盖范围和限制 | 根 [README](../README.md) |

任务状态以文件头为准，此处不维护重复状态表。默认不加载 done、cancelled 计划及 rejected、superseded 设计；调查历史取舍时再读取。产品构想、决定成立、工程实现、验证通过是不同状态。

## 技能分工与接入

以高效迭代、可靠交付和保留探索空间为目标，按任务选择相关能力；不要求每次依次经过产品、界面与工程三套完整流程。已有事实与决定直接引用，交接只补充本次目标、尚缺条件和验证方式。

| 主力技能 | 主要职责与使用场景 | 结果归属与边界 |
| --- | --- | --- |
| [PM Skills](https://github.com/phuryn/pm-skills) | 用户问题、价值、范围、假设与验证；用于产品探索、取舍和反馈分析 | 有价值的结果更新 `product.md`，区分确认与建议，不另建同范围 PRD |
| [Impeccable](https://github.com/pbakaus/impeccable) | 信息组织、交互、视觉与界面审查；用于原型探索、界面实现和改进 | 产品语义归产品文档，实际组件与样式归代码；界面表现不能证明业务可行 |
| [Superpowers](https://github.com/obra/superpowers) | 技术方案、任务拆分、调试、测试与交付；用于复杂实现和缺陷修复 | 长期取舍与交接按下文建档，实际实现归架构文档；技术正确性仍需测试与实测 |

这是项目选用约定，不表示三类技能均已安装或完成联合验收。普通修改选用相关单项能力；原型、技术试验和用户反馈可以返回产品探索，不自动触发排期。3D 质量、显存、可编辑性和格式兼容需要专项验证，不能由技能名称或流程完成替代。

技能的默认目录、模板与执行流程以用户要求和本项目约定为边界：复用已有需求，普通修改不额外强制建档，不自动提交、发布或启动多 agent。需要记录时沿用本文状态与章节；存在冲突时说明差异，不通过修改第三方技能解决。工具确需固定文档入口时，先验证能否读取主要文档或导航链接，不维护第二份独立正文；无法适配时暂不启用该入口并说明限制。

接入依据与边界：Impeccable 当前初始化会写 `PRODUCT.md`，并有生成 `DESIGN.md` 的流程；Superpowers 的 [设计流程](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md) 和 [计划流程](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md) 有默认路径与审阅步骤，其 [项目指令优先规则](https://github.com/obra/superpowers/blob/main/skills/using-superpowers/SKILL.md) 允许项目约定覆盖。这里只采用相关能力，不复制上游整套流程；接入时核对实际安装版本。

首次接入或升级影响执行方式时，核对来源、版本、默认产物和自动执行行为，包括 hooks、提交与子 agent；优先使用安装机制已有的版本记录，不另建技能管理系统。用相关真实任务检验：产品讨论不擅自开始实施，局部 UI 修改不重复定义产品，缺陷修复有原因与回归证据，复杂任务能凭仓库接续且不重复建档。缺少应用或其他真实条件时记录待验证项，不能将阅读规则当作联合验收。技能与接入配置的变更单独审阅。

## 何时更新或新增文档

- 产品头脑风暴允许先探索模糊问题与不同方向，需要比较时说明各自价值和未知条件，不机械凑满固定数量。值得保留的结果更新 `product.md` 对应章节中的用户确认、候选建议与待验证问题，不按聊天轮次追加纪要；暂缓但仍有价值的想法保留动机与重新考虑条件。技术资料可以作为简短研究线索，不能把研究建议写成已定方案。
- `architecture.md` 只随真实工程状态变化更新。产品增加功能或确认版本范围，不代表技术方案已定，也不自动触发设计、排期或开发。
- 具体技术设计任务开始后，只有需要比较方案或保存长期取舍理由时，才在 `design/` 建立针对该问题的记录；ADR 也放在这里。普通产品讨论不创建技术设计记录，accepted 必须有明确的决定依据，不能由 agent 将自己的建议升级为决定。
- 已开始的研究、验证或实施任务确需跨会话交接、或失败恢复复杂时，才在 `plans/` 建立执行计划；记录明确目标、进展和证据。头脑风暴持续多轮不等于已开始执行任务，小修改直接完成。
- 原型或试验标明验证的问题与适用限制；只有产生稳定且需要独立维护的界面规范时，再确定其唯一维护位置及工具兼容方式，不预建 UI 模板库。可执行的组件与样式由代码维护，文档解释必要原则与约束。
- 默认更新内容的主要维护位置，其他文档只在摘要失真或链接受影响时同步修改。拆分应由独立维护需要驱动，不因文件长度或参考项目有某个目录就机械拆分。

事实归属与技能职责借鉴 [DeepSeek 的文档约定](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/AGENTS.md)：每条事实有主要位置，技能保存可复用方法；本项目按实际内容保留较少层级。

## 命名与拆分

- 长期说明采用稳定主题名，如 `product.md`。任务与设计使用首次创建日期和具体主题：`YYYY-MM-DD-topic.md`，小写英文和连字符，不加递增编号。
- 改变状态不改名、不移动；同日重名时细化主题。`design/` 与 `plans/` 是保留的骨架目录，暂无记录时使用 `.gitkeep`，不删除空目录，也不为填满目录编写内容；其他目录按实际需要建立。
- 子系统需要独立维护时再拆专题，由入口链接其主要说明。不要按每个产品版本复制整套文档；版本与历史内容按下节处理。

## 跨版本维护

- **区分四类事实。** `product.md` 分开说明当前确认的目标与后续候选，不逐版堆叠旧需求；`architecture.md` 对应当前检出代码的实际状态。实现、检查通过与已发布分别记录，不能因计划 done 或代码已合入就声称发布。以后有应用版本清单和正式发布记录时分别引用它们，不在多份说明中手写重复版本号；没有发布证据时不得推断已发布。
- **日常文档持续更新。** 功能改变时修改原有主题正文，保留仍有效的约束；旧版本的全文从真实存在的 Git 提交或发布标签查阅。首个实际发布开始，在一个选定位置维护发布变化记录，区分未发布与已发布内容；不把发布历史追加进产品正文，也不重写过去发布的含义。当前不预建发布目录或空日志。
- **迁移由兼容影响触发。** API、配置或持久数据变化需要用户采取动作时，同次交付写明受影响版本、迁移方法、验证和恢复限制，即使只支持最新版本也不能省略。只有确实同时维护多个版本且行为不同，才增加带适用范围的说明；停止支持时更新当前导航，但仍被迁移或兼容代码依赖的约束继续保留。
- **历史按使用价值收敛。** 已完成计划压缩为结果、证据与限制。设计取舍改变时另建替代记录，不能将旧决定改写成相反结论；只有部分被替代时写清仍有效的范围。仍能解释兼容、安全、数据语义或避免重复踩坑的理由保持可发现；完全失去当前指导作用的记录退出默认阅读。清理前保留仍有价值的独有理由并修复入链，不以年龄、文件数量或「Git 应该有」作为依据；未保存的历史聊天与 `.tmp/` 不算持久记录。

采用边界：以上借鉴 [DeepSeek 的版本事实分离](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/session-format-status.md)、[Agent Notes 生命周期](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/README.md) 和 [Pi 的发布记录规则](https://github.com/badlogic/pi-mono/blob/main/AGENTS.md#changelog)。本项目保留现有文件名与状态方式，不复制其多层分类、双语配对、冻结归档清单或专用数据版本系统。

## 任务记录

`plans/` 下的 Markdown 文件在标题之后、首个二级标题之前写唯一状态行：`状态：active`、`状态：done` 或 `状态：cancelled`。

使用四个二级章节：`目标与验收`、`当前进展`、`验证证据`、`下一步`。验收条件可用复选框。

- active：包括缺材料或暂时阻塞的任务，在下一步写清阻塞条件及可执行动作。
- done：必须有实际验证结果，不能留未完成的验收复选框。完成后压缩为结果、验证、剩余限制与必要链接，不保留逐轮聊天或工具日志。
- cancelled：在当前进展说明取消原因，不能假装完成。

## 提案与决定

`design/` 下的记录同样在文件头写唯一状态行：`状态：proposed`、`状态：accepted`、`状态：rejected` 或 `状态：superseded`。使用四个二级章节：`问题`、`方案与取舍`、`影响`、`验证状态`；需要时在章内加三级标题。

accepted 只说明决定成立，不代表代码、模型或部署已实现。rejected 说明拒绝理由；superseded 保留原有取舍，但不能继续作为当前规则。

替代决定时，旧记录增加单独一行 `替代记录：[新决定](新文件.md)`，新记录增加 `替代来源：[历史：旧决定](旧文件.md)`。双方互链；后继也被替代时保留这条历史链。当前导航应链接最新有效记录，其他文档确需引用旧记录时，链接文字必须以 `历史：` 开头，表明其历史用途。

## 维护与验证

每次交付审阅本次改动涉及的三点：是否把建议升级成事实；当前说明、已确认目标与实际实现是否一致；被替代内容、入链及旧版本兼容是否处理。发现矛盾时记录差异并核实意图，不能只把文档改成与代码一样。

| 工作 | 对应证据 |
| --- | --- |
| 产品讨论 | 用户确认、研究依据、保留的未知项 |
| UI 与交互 | 实际页面与主要操作路径、错误和空状态、适用的可访问性检查 |
| 工程实现 | 构建与静态检查、行为测试及相关失败路径 |
| 生成模型或处理流程调整 | 代表性样本的效果、可编辑性、等待、失败重试与总成本；分别验证确定性程序行为与生成效果 |
| 数据或配置迁移 | 适用的旧数据或旧配置路径、迁移结果与恢复限制 |

可机械判定的规则用已有检查器及失败样例验证；语义与业务效果由对应任务的实际证据和审阅判断。检查选择借鉴 [DeepSeek 的按改动验证流程](https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/skills/dsh-pre-push-checks/SKILL.md)，保留本项目的 PowerShell 入口。新增自动规则前应有具体失误场景及稳定判定方法，不能用关键词扫描代替业务判断，也不因新规则就为普通修改强制写计划。

根入口以约 80 行以内为编辑目标，不设机械字数门禁。检查器只检验格式、链接和记录结构；内容是否准确、是否值得保留，由本次任务的审阅和实际验证判断。检查能力及使用方式见根 [README](../README.md)。长期稳定性依赖持续维护和真实测试，不由目录布局保证。
